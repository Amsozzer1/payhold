# Design notes

Why each decision was made, what was tried and dropped, and what the numbers changed.

## 1. Two layouts per document type, kept
**Chose:** two layouts each for the rate con, the BOL/POD and the invoice, with different labels, column order, money and identifier formats.
**Because:** one layout per type would let the extractor work by fixed coordinates, and the round-trip test would prove nothing. With two, the load number prints as `4820157` on one and `482-0157` on the other, the BOL number as `30418827` and `3041 8827`, and the load key has to come out the same.
**Tried first / what went wrong:** the plan allowed cutting to one layout for the rate con and BOL to save time, but only if decided at the start. It was not cut.

## 2. What payhold sees and what only the scorer sees
**Chose:** the generator writes three files per seed. `world.json` is what payhold may read (carrier registry, remit-to history, factors, pre-stream paid and rejected requests). `requests.json` is what a factor submits (request id, factor, time, three PDFs). `truth.json` holds the labels and is read only by the eval.
**Because:** it makes it hard for a check to accidentally read a label.

## 3. Bank-change packets get their own carriers
**Chose:** every planted bank change and every "verified recent bank change" look-alike uses a carrier that appears in no other packet.
**Because:** a remit-to change on a busy carrier would also change what the right answer is for that carrier's other packets that week. Keeping them apart means every packet has exactly one known answer.

## 4. "Seen before" split into two checks
**Chose:** the plan's rule (hold if the load was seen from a different factor in any status, or paid by anyone) is two checks. `duplicate_rebill` looks at the same factor (paid or pending, rejected ignored). `double_factoring` looks at other factors (any status for the load key, paid for the invoice key).
**Because:** the reason line then says which problem it is, and each planted issue type maps to one reason code. On the dev seeds every hold carried exactly the code of its own issue type and nothing else.

## 5. The carrier name check accepts the DBA on file
**Chose:** the BOL carrier name passes if, after dropping punctuation and legal suffixes, it matches the rate con name, or the registry's legal name or DBA for that USDOT number.
**Because:** the registry has DBAs, and a carrier using its DBA on paperwork is normal. Main-stream BOLs print only the legal name, so on the main stream this rule never decides anything.
**Note:** this was written before the freeze and before the held-out set was opened. The plan says carriers have DBAs, so this rule may anticipate a held-out kind. The held-out row should be read with that in mind.

## 6. The payout claim is a conditional write, and a read-then-write control shows why
**Chose:** one conditional put on `paid_bills` takes a lease (`attribute_not_exists(pk) OR (same request AND pending AND lease expired)`). Only the holder of the attempt token calls the rail, then marks the item sent with a condition on its token. A loser does a consistent read to tell a duplicate from a retry.
**Tried first / what went wrong:** to check that the 50-client trial could fail at all, the same trial ran with a read-then-write claim (read the item, write if absent). That control sent 5 to 37 payouts per load over 100 trials (`results/payout_naive_control.json`). The conditional write sent exactly 1 in every trial. The control is a race, so its numbers change from run to run.

## 7. 50 clients built once per scenario, not per trial
**Chose:** the 50 DynamoDB clients are built one after another, each from its own boto3 session, before any trial starts. Each trial then lines all 50 threads up on a `threading.Barrier(50)` against a fresh load key.
**Because:** building 5,000 clients would take minutes and test boto3 startup, not the claim. A fresh key per trial keeps trials independent.

## 8. Extraction passed its round-trip on the first run
**What happened:** the first run of the round-trip (every field of 1,500 PDFs, seed 1 and dev seeds 101-102, 54,000 field checks) had 0 failures.
**What it means:** the PDFs are generated by the same code that defines the labels, with no scanning noise. It shows that the label anchoring and normalization work on both layouts. It does not show anything about real paperwork, and the README says so.

## 9. Thresholds
**Chose:** padding tolerance $0, recent remit-to change window 30 days, payout lease 300 s. Set on dev seeds 101-102. The generator plants recent changes 1-5 days before a request and background changes 120-700 days before, so any window between 5 and 120 days gives the same dev-seed result. 30 days sits well inside that range.

## 10. The money-shot data was missing from the first results commit
**What happened:** after the first `make eval` on the report seeds, `git status` listed the new files in `results/` but nothing under `web/public/data/`. The `.gitignore` line `data/` (meant for generated PDFs at the repo root) matched every directory named `data`, including the page's export.
**Fix:** anchored the pattern to the root (`/data/`). Caught before the commit, so no results were lost, but the page would have built in CI from data that never reached the repo.

## 11. Page dependencies chosen for their licenses
**Chose:** Tailwind 3.4 instead of 4, and a local empty stub in place of `sharp`.
**Because:** the repo allows no copyleft dependencies. Tailwind 4 pulls in `lightningcss` (MPL-2.0). Next.js lists `sharp` as an optional dependency, and sharp downloads prebuilt libvips binaries under LGPL; the page is a static export with plain `<img>` tags, so image optimization never runs and the stub is never loaded. Next.js telemetry is switched off with `NEXT_TELEMETRY_DISABLED=1` in the Makefile and CI.

## 12. The featured packet is the fourth one
**What happened:** the plan picks the first double-factoring follower in seed 1 that the baseline paid and payhold held. In seed 1 that is the fourth packet (request S1-0004), 35 synthetic minutes after its first request. It was kept rather than hand-picking a later one, so the GIF shows the replay first and then opens the packet once the replay ends.

## 13. Page images cropped to the field area
**Chose:** the page PNGs are full 100 dpi pages, and the detail view crops them to the top of the page where the identifiers sit.
**Because:** three full letter pages side by side in a 1,000 px GIF leave the boxed numbers unreadable. Cropping keeps the boxes and labels legible without a second export.
